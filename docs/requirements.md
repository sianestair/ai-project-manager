# AI 项目经理：需求与目标

状态：第一版需求基线（已确认）
阶段：实现
架构基线：[architecture.md](architecture.md)
分支：`develop`

## 1. 为什么重新开始

上一版 `project-manager` 同时引入了多套工件、流程状态、角色、CLI 和项目专用规则。每一部分解决了局部问题，但缺少一条稳定、清晰、可以从头走到尾的主线，导致项目目标、产品需求、流程设计和实现机制分散在不同位置。

本次重建不以兼容或整理上一版为目标，而是从空白基线重新回答：

1. 我们为什么需要 AI 项目经理。
2. AI 项目经理要帮助谁完成什么工作。
3. 一个项目变化应如何经过需求、设计、实现和验收。
4. 哪些职责属于 AI 项目经理，哪些决策必须由用户完成。
5. 满足什么条件，第一版才算真正可用。

## 2. 产品目标

建立一个面向真实软件项目的 AI 项目经理。用户只需要表达业务意图和做关键决策，AI 项目经理负责把变化持续推进为明确需求、可评审设计、可执行实现和可验证结果。

第一版首先追求：

- 主流程清楚，用户随时知道当前处于什么阶段。
- 用户可以从不完整、含糊甚至彼此矛盾的表达开始，由 AI 项目经理负责整理为可确认的需求。
- 每一阶段都有明确目的、输入、输出和完成条件。
- 需求、设计与实现之间可以追溯，不依赖聊天记录维持上下文。
- 发现问题时允许回到上一阶段修正，而不是强行单向推进。
- 只在确实需要业务或重大技术取舍时请求用户决定。
- 结构保持最小，尚未被真实需求证明必要的机制不进入第一版。

## 3. 目标用户

第一目标用户是软件项目的业务负责人或项目负责人。他可能能够判断业务目标和最终效果，但不希望亲自维护复杂的 AI 工作流、Agent 路由、状态文件或内部工具命令。

## 4. 核心工作流程

第一版采用以下主流程：

```text
提出意图
-> 需求整理与确认
-> 设计与确认
-> 实现与验证
-> 验收与知识确认
-> 更新项目当前状态
-> 完成并归档
```

流程允许回退：

- 设计发现需求不完整时，回到需求阶段。
- 实现发现设计不可行时，回到设计阶段。
- 验收未通过时，根据原因回到需求、设计或实现阶段。
- 验收和知识确认时，如果用户提出的调整改变了已确认需求或设计，必须回到受影响的阶段，完成修改、实现和重新验证后再确认。

当前暂不决定具体状态机、文件数量、CLI 或 Agent 结构。这些属于后续架构设计。

## 5. 核心需求

### R1. 单一用户入口

用户应当只需要与 AI 项目经理交互，不需要知道内部使用了哪些角色、Skill、Agent、模板或工具。

### R2. 先明确为什么和目标

用户最初表达的是变化意图，不自动等于已确认需求。AI 项目经理必须通过读取项目当前状态、调研、澄清矛盾、补充遗漏和提出建议，把意图整理为用户可以判断的需求方案。

任何变化在进入设计前，必须由用户确认：

- 为什么要做。
- 要解决什么问题。
- 预期达到什么结果。
- 包含哪些范围。
- 明确不包含哪些范围。
- 如何判断需求已经满足。

用户确认后形成当前 Change 的需求基线。只要后续发现会改变该基线，就必须重新请求用户确认；不改变需求基线的分析和执行工作由 AI 项目经理继续推进。

### R3. 需求与方案分离

需求描述需要达到的结果、行为和约束；设计描述选择怎样的架构和方案满足需求。不得因为已有实现方便，就反向修改或隐含替代需求。

### R4. 设计可评审

进入实现前，应当形成足以评审和实施的设计。设计需要按变化实际涉及的范围说明架构、模块职责、数据、接口、交互、安全、风险和关键取舍，而不是要求每次机械填写所有类别。

AI 项目经理必须向用户提交可理解的设计结论和关键取舍。改变产品行为、系统边界、重要架构、安全、资金、权限、数据责任或形成长期技术约束的设计，需要用户确认后才能进入实现；确认范围内的局部实现设计由 AI 项目经理自主决定。

### R5. 实现有明确依据

实现必须以已确认的需求和设计为依据。实施过程需要记录任务状态、实现偏差、验证结果和新发现的问题。

### R6. 结果可验收

完成不能只表示代码已经写完。项目经理需要根据需求目标和设计约束组织验证，并向用户说明：

- 已完成什么。
- 如何验证。
- 哪些目标已经满足。
- 哪些问题仍然存在。
- 是否需要用户进行最终确认。

验收分为两部分：先用测试和证据验证实现是否符合已确认需求与设计，再由用户确认交付结果和准备提升为项目当前状态的知识。工具验证通过不等于用户已经完成最终确认。

### R7. 过程可恢复

新的会话应当能够从项目内的持久化内容恢复当前目标、已确认结论、当前阶段、未解决问题和下一步，而不依赖完整聊天历史。

过程恢复必须遵守 R12 定义的状态来源：新工作从项目当前状态开始，未完成工作从项目当前状态与对应 Change 状态共同恢复。

### R8. 最小化内部复杂度

第一版不因为未来可能需要而预先建立复杂状态机、多层角色体系或大量强制工件。新增机制必须能够解决已经出现且无法由现有结构清楚处理的问题。

### R9. Agent 支持范围

支持多个编码 Agent 是产品需求。AI 项目经理的需求、流程语义、项目内持久化信息和确定性运行时不应依赖某个特定模型或 Agent 才能成立。

第一阶段只要求完整支持并验收 Codex。其他 Agent 应按“完整支持”或“标准兼容”分级，不在缺少安装方式、能力映射和验收证据时宣称完整支持；它们不属于第一阶段交付范围。

Codex 的 Skill、工具、会话机制和插件能力可以用于第一版实现，但这些属于 Codex 适配器，不应替代产品核心需求。详细调研和建议范围见 [Agent 支持调研](agent-support-research.md)。

### R10. 验收后更新项目知识

验收后的知识更新属于第一版必备能力，但验证通过后不能自动更新项目当前知识。

AI 项目经理必须整理本次变化准备提升的知识，包括产品事实、业务或工程规则、关键决策及其原因，以及会长期约束后续工作的架构或技术方案，并提交用户确认。普通代码结构、依赖版本和可局部替换的实现细节默认不作为项目知识，除非它们形成了长期约束。

用户可以确认、排除或修改候选知识。如果修改只是在纠正文案和知识归属，可以重新整理后确认；如果修改改变了需求、设计或实现，Change 必须回到最早受影响的阶段，完成重新确认、实现和验证。

只有交付结果与候选知识都获得用户确认后，才能把知识提升为项目当前状态，并完成 Change。

未验收的目标、讨论过程、候选方案和实现中的临时结论不得提前成为项目当前知识。

### R11. 决策权限必须有明确策略

第一版必须定义一套可理解、可检查的决策权限策略，用来判断哪些事项由 AI 项目经理自主推进，哪些事项必须由用户确认。

这套策略不能依赖用户在每次变化开始时临时列出全部规则。它至少需要考虑业务行为、范围变化、重大架构取舍、安全、资金、权限、不可逆操作、验收标准和最终确认等风险类型，并允许项目在必要时增加自己的约束。

默认责任原则是：

- AI 项目经理负责理解意图、发现表达与真实目标之间的矛盾、调研、整理需求、提出设计方案和推荐结论。
- 用户负责确认需求基线、影响重大的设计取舍、需求或关键设计变更、最终验收结果和知识提升。
- 需求和关键设计确认后，AI 项目经理在确认范围内自主完成详细设计、实施、测试、证据整理和非阻塞问题处理。
- AI 项目经理不能因为用户最初没有想到某个细节，就默认替用户作出会改变产品目标或长期约束的决定；应整理影响和建议后请求确认。
- 不影响已确认需求和关键设计的局部、可逆实现调整，不需要反复请求用户确认。

### R12. 区分项目当前状态与 Change 状态

受管理项目必须提供稳定、可发现的项目材料约定，至少区分：

- `knowledge-base/`：用户已经确认、对后续工作有效的项目知识。
- `engineering/`：项目当前工程实现和可执行验证。
- `changes/active/`：尚未完成的 Change 及其需求、设计、实施、验收和待提升知识。
- `changes/archived/`：已完成 Change 的历史证据。

这些目录的内部结构和是否允许配置由设计阶段决定，但它们的职责边界属于产品需求。

系统必须遵守以下状态来源原则：

1. 新的工作基于项目当前状态启动。项目当前状态由已确认项目知识、当前工程实现和项目级约束共同构成。
2. 未完成工作的恢复基于项目当前状态与对应的 active Change 状态。
3. active Change 中未确认的目标、方案和结论不是项目当前状态。
4. 已完成 Change 不作为当前状态来源，只作为历史追溯和审计证据。
5. 项目当前知识只能通过用户确认后的知识提升发生变化。

## 6. 第一版非目标

- 不迁移、兼容或改写上一版实现。
- 本需求基线不选择插件、Skill、CLI 或运行时架构；这些选择进入架构设计阶段。
- 本需求基线不实现代码；实现需等待设计达到对应确认条件。
- 不预先建设面向所有类型项目的完整平台。
- 不预先加入未经真实项目验证的复杂协作机制。

## 7. 第一版成功标准

第一版至少应能通过一个真实项目变化证明：

1. 用户可以从“实现连接钱包登录”这一真实功能意图开始。
2. AI 项目经理能够发现表达缺口并整理出供用户确认的需求，而不是直接把原始表达当成需求。
3. 用户确认需求基线和关键设计取舍后，AI 项目经理能够自主持续推进实现。
4. 新发现不改变需求和关键设计时，不需要反复打断用户；发生改变时能够回到对应阶段重新确认。
5. 最终结果能够根据已确认需求和设计进行验证，并由用户完成验收确认。
6. AI 项目经理能够整理候选知识，由用户确认后更新项目当前知识。
7. 如果知识确认引发需求或设计变化，能够重新进入修改、实现和验收循环。
8. 新 Change 只从项目当前状态启动，不依赖已归档 Change 推导现状。
9. 中断的 Change 能够从项目当前状态与该 Change 状态恢复并继续工作。
10. 用户不需要直接操作内部 Agent 或流程工具。
11. 上述过程在 Codex 中完成第一阶段实现和验收。

## 8. 已确认结论

- 支持多个编码 Agent 是正式产品需求。
- 第一阶段只完整支持并验收 Codex，其他 Agent 不属于第一阶段交付范围。
- 第一版使用“实现连接钱包登录”作为真实功能验证案例。
- 验收后的项目知识更新属于第一版必备能力，且必须经过用户确认才能提升为项目当前状态。
- 用户与 AI 项目经理之间的决策权限需要形成规则或策略，不能要求用户现在逐项凭感觉决定。
- 用户的原始表达是待整理的意图，不自动等于需求；AI 项目经理负责整理需求，用户负责确认需求基线。
- 系统必须区分项目当前状态和 Change 过程状态。
- 新工作基于项目当前状态；未完成工作的恢复基于项目当前状态与对应 Change 状态；已完成 Change 只用于历史追溯。

## 9. 已明确的状态与材料原则

### 9.1 项目当前状态

项目当前状态是新的工作可以直接依赖的基线，包括：

- 已经由用户确认的项目知识。
- 当前工程实现和验证能力。
- 对整个项目长期有效的约束与配置。

项目当前状态不从历史 Change 拼接得出，也不由 Agent 根据聊天记录自行推断。

### 9.2 Change 状态

Change 状态服务于一次尚未完成的变化，包括原始意图、已确认需求、设计、实施进度、验证证据、未解决问题和待确认知识。

恢复该 Change 时需要同时读取项目当前状态，因为项目基线可能包含该 Change 没有重复记录的长期事实和规则。

### 9.3 历史 Change

Change 完成后进入历史区域，保存当时为什么改变、如何设计、怎样实现和如何验收的证据。

历史 Change 可以用于追溯原因和审计过程，但不能覆盖项目当前知识，也不能成为新工作的默认输入。

## 10. 架构设计阶段需细化的策略

### 10.1 设计确认分级

R4 已经确定重要设计需要用户确认、局部实现设计由 AI 项目经理自主决定。设计阶段仍需给出可执行的分类标准和例子，避免“重要”完全依赖临场判断。

### 10.2 知识提升包

设计阶段需要定义 AI 项目经理如何向用户展示候选事实、规则、决策和长期技术方案，以及用户如何确认、排除、修改或要求回退。

### 10.3 项目材料约定

设计阶段需要定义 `knowledge-base/`、`engineering/`、`changes/active/` 和 `changes/archived/` 的最小内部结构、定位方式、初始化方式和完整性检查。

### 10.4 Agent 后续支持顺序

[Agent 支持调研](agent-support-research.md) 中的 Claude Code、GitHub Copilot、Gemini CLI、OpenCode、Cursor、Windsurf、Cline 和 Roo Code 结论保留为后续规划参考。第一阶段不需要决定或实现它们的完整适配顺序。

## 11. 推迟到设计阶段的问题

以下问题不要求用户在需求阶段决定：

- 使用几个目录和文档。
- 哪些内容合并在同一个文件中。
- 是否需要 CLI、状态机或配置文件。
- 是否以及如何使用 Skill、子 Agent、Hook 或插件。
- 各 Agent 的安装、Manifest、命令、Hook、权限和子 Agent 如何通过适配器实现。
