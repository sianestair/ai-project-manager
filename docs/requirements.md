# AI 项目经理：需求与目标

状态：草案  
阶段：需求梳理  
分支：`develop`

## 1. 为什么重新开始

上一版 `project-manager` 同时引入了多套工件、流程状态、角色、CLI 和项目专用规则。每一部分解决了局部问题，但缺少一条稳定、清晰、可以从头走到尾的主线，导致项目目标、产品需求、流程设计和实现机制分散在不同位置。

本次重建不以兼容或整理上一版为目标，而是从空白基线重新回答：

1. 我们为什么需要 AI 项目经理。
2. AI 项目经理要帮助谁完成什么工作。
3. 一个项目变化应如何经过需求、设计、实现和验收。
4. 哪些职责属于 AI 项目经理，哪些决策必须由用户完成。
5. 满足什么条件，第一版才算真正可用。

## 2. 产品目标

建立一个面向真实软件项目的 AI 项目经理。用户只需要表达业务意图和做关键决策，AI 项目经理负责把变化持续推进为明确需求、可评审设计、可执行实现和可验证结果。

第一版首先追求：

- 主流程清楚，用户随时知道当前处于什么阶段。
- 每一阶段都有明确目的、输入、输出和完成条件。
- 需求、设计与实现之间可以追溯，不依赖聊天记录维持上下文。
- 发现问题时允许回到上一阶段修正，而不是强行单向推进。
- 只在确实需要业务或重大技术取舍时请求用户决定。
- 结构保持最小，尚未被真实需求证明必要的机制不进入第一版。

## 3. 目标用户

第一目标用户是软件项目的业务负责人或项目负责人。他可能能够判断业务目标和最终效果，但不希望亲自维护复杂的 AI 工作流、Agent 路由、状态文件或内部工具命令。

## 4. 核心工作流程

第一版采用以下主流程：

```text
提出变化
-> 需求
-> 设计
-> 实现
-> 验收
-> 完成
```

流程允许回退：

- 设计发现需求不完整时，回到需求阶段。
- 实现发现设计不可行时，回到设计阶段。
- 验收未通过时，根据原因回到需求、设计或实现阶段。

当前暂不决定具体状态机、文件数量、CLI 或 Agent 结构。这些属于后续架构设计。

## 5. 核心需求

### R1. 单一用户入口

用户应当只需要与 AI 项目经理交互，不需要知道内部使用了哪些角色、Skill、Agent、模板或工具。

### R2. 先明确为什么和目标

任何变化在进入设计前，必须明确：

- 为什么要做。
- 要解决什么问题。
- 预期达到什么结果。
- 包含哪些范围。
- 明确不包含哪些范围。
- 如何判断需求已经满足。

### R3. 需求与方案分离

需求描述需要达到的结果、行为和约束；设计描述选择怎样的架构和方案满足需求。不得因为已有实现方便，就反向修改或隐含替代需求。

### R4. 设计可评审

进入实现前，应当形成足以评审和实施的设计。设计需要按变化实际涉及的范围说明架构、模块职责、数据、接口、交互、安全、风险和关键取舍，而不是要求每次机械填写所有类别。

### R5. 实现有明确依据

实现必须以已确认的需求和设计为依据。实施过程需要记录任务状态、实现偏差、验证结果和新发现的问题。

### R6. 结果可验收

完成不能只表示代码已经写完。项目经理需要根据需求目标和设计约束组织验证，并向用户说明：

- 已完成什么。
- 如何验证。
- 哪些目标已经满足。
- 哪些问题仍然存在。
- 是否需要用户进行最终确认。

### R7. 过程可恢复

新的会话应当能够从项目内的持久化内容恢复当前目标、已确认结论、当前阶段、未解决问题和下一步，而不依赖完整聊天历史。

### R8. 最小化内部复杂度

第一版不因为未来可能需要而预先建立复杂状态机、多层角色体系或大量强制工件。新增机制必须能够解决已经出现且无法由现有结构清楚处理的问题。

### R9. 产品行为不绑定特定 Agent

AI 项目经理的需求、流程语义和项目内持久化信息不应依赖某个特定模型或 Agent 才能成立。

第一版明确以 Codex 作为实现和验证环境。Codex 的 Skill、工具、会话机制和插件能力可以用于实现，但这些属于设计与实现选择，不应替代产品需求本身。

### R10. 验收后更新项目知识

验收后的知识更新属于第一版必备能力。一个变化验收通过后，AI 项目经理必须把已经确认并对后续工作长期有效的事实、规则和关键决策更新到项目当前知识中。

未验收的目标、讨论过程、候选方案和实现中的临时结论不得提前成为项目当前知识。

### R11. 决策权限必须有明确策略

第一版必须定义一套可理解、可检查的决策权限策略，用来判断哪些事项由 AI 项目经理自主推进，哪些事项必须由用户确认。

这套策略不能依赖用户在每次变化开始时临时列出全部规则。它至少需要考虑业务行为、范围变化、重大架构取舍、安全、资金、权限、不可逆操作、验收标准和最终确认等风险类型，并允许项目在必要时增加自己的约束。

## 6. 第一版非目标

- 不迁移、兼容或改写上一版实现。
- 当前阶段不选择插件、Skill、CLI 或运行时架构。
- 当前阶段不实现代码。
- 不预先建设面向所有类型项目的完整平台。
- 不预先加入未经真实项目验证的复杂协作机制。

## 7. 第一版成功标准

第一版至少应能通过一个真实项目变化证明：

1. 用户可以从“实现连接钱包登录”这一真实功能意图开始。
2. AI 项目经理可以协助形成明确需求和目标。
3. 在用户确认关键取舍后形成可实施设计。
4. 实现工作能够依据设计持续推进。
5. 最终结果能够按需求进行验证和验收。
6. 验收通过后能够把确定性结论更新为项目当前知识。
7. 中断会话后能够恢复上下文并继续工作。
8. 用户不需要直接操作内部 Agent 或流程工具。
9. 上述过程在 Codex 中完成第一版实现和验证。

## 8. 已确认结论

- 产品需求不绑定特定 Agent 或模型。
- 第一版在 Codex 中实现和验证。
- 第一版使用“实现连接钱包登录”作为真实功能验证案例。
- 验收后的项目知识更新属于第一版必备能力。
- 用户与 AI 项目经理之间的决策权限需要形成规则或策略，不能要求用户现在逐项凭感觉决定。

## 9. 仍需澄清的需求问题

### 9.1 项目当前知识与变化过程是否需要明确区分

这个问题关心的不是目录怎么命名，而是信息的权威状态。

例如，在“实现连接钱包登录”的过程中会同时出现：

- 已经成立的项目现状。
- 本次希望新增的登录行为。
- 尚未确定的候选方案。
- 最终选定的设计。
- 实际代码和测试结果。
- 验收后对项目现状形成的新结论。

需要确认的是：后续 AI 开始新变化时，是否必须能够直接识别“当前已经验收并成立的知识”，而不需要翻阅历史变化、讨论记录或根据代码猜测。

建议答案是“需要”。如果确认，这会成为产品需求；至于使用哪些目录和文件实现，留到设计阶段决定。

### 9.2 哪些信息属于整个项目，哪些信息只属于一次变化

这个问题关心的是跨会话恢复时，信息的有效期和作用范围。

项目长期信息可能包括项目名称、项目目标、当前知识位置、工程位置和长期约束。单次变化信息可能包括为什么做、范围、需求、设计、实施进度、验收结果和未解决问题。

需要确认的是：第一版是否必须区分项目级信息和单次变化信息，防止一个变化的临时结论被误当成整个项目的长期规则。

建议答案是“需要”。具体保存字段和文件结构属于设计问题。

### 9.3 决策权限策略

需要继续设计一套默认策略，至少明确：

- 哪些低风险、可逆工作由 AI 项目经理自主推进。
- 哪些业务、范围、架构、安全、资金和权限决策必须由用户确认。
- 什么情况属于执行已确认设计，什么情况已经构成设计变更。
- 验收、知识更新和完成是否需要用户最终确认。

## 10. 推迟到设计阶段的问题

以下问题不要求用户在需求阶段决定：

- 使用几个目录和文档。
- 哪些内容合并在同一个文件中。
- 是否需要 CLI、状态机或配置文件。
- 是否以及如何使用 Skill、子 Agent、Hook 或插件。
- Codex 之外的平台如何适配。
